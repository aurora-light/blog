单机运行定时任务时，往往只需要一个 `@Scheduled`。但服务部署两个实例后，每个实例都会按照自己的定时配置触发任务，同一批短信就可能被处理两遍。

这篇笔记来自项目中的定时通知任务：后台启用 Spring 调度和 ShedLock，通过共享数据库协调执行。代码片段进行了通用化，不包含真实业务数据；下面列出的实验是验证方法，不是已经完成的线上验证。

## 一、为什么单机锁不够

```text
每天指定时间
实例 A → 扫描待通知记录 → 发送短信
实例 B → 扫描待通知记录 → 发送短信
```

两个 JVM 不共享内存，在 A 中加 `synchronized` 无法阻止 B。需要把锁状态放到两个实例都能访问的存储中。

项目使用 `JdbcTemplateLockProvider`，通过数据库保存锁。所有参与协调的实例必须使用同一套有效的锁存储，并采用相同锁名。

## 二、项目中的三处配置

第一处是后台启动类：

```java
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "10m")
```

第一项启用 Spring 定时任务；第二项启用 ShedLock 集成并设置默认最大锁时长。

第二处是锁提供者，下面保留项目现有配置的关键部分：

```java
@Bean
public LockProvider lockProvider(DataSource dataSource) {
    return new JdbcTemplateLockProvider(
            JdbcTemplateLockProvider.Configuration.builder()
                    .withJdbcTemplate(new JdbcTemplate(dataSource))
                    .build()
    );
}
```

它依赖 `DataSource`、Spring JDBC、ShedLock Spring 集成与 JDBC Provider。还需要按数据库类型和项目使用的版本初始化锁表，不能只加注解就认为配置完成。

第三处是具体任务上的注解。通用化示例为：

```java
@Scheduled(cron = "${notice.cron:0 40 8 * * ?}")
@SchedulerLock(
        name = "dailyNoticeTask",
        lockAtMostFor = "5m",
        lockAtLeastFor = "4s"
)
public void sendNotice() {
    // 查询符合条件的记录并处理
}
```

示例 cron 表示每天 8:40 触发，具体时区应在应用或注解中明确配置，避免不同实例采用不同系统时区。

## 三、没抢到锁的实例会怎样

```text
实例 A：获得 dailyNoticeTask 锁 → 执行
实例 B：没有获得相同锁       → 跳过本次执行
```

ShedLock 不是任务队列。没有获得锁的实例不会排队等待并在稍后自动补跑。[ShedLock 官方说明](https://github.com/lukas-krecan/ShedLock)

两个不同业务任务应使用不同的锁名；同一业务任务在不同实例上则应使用一致的锁名。

## 四、两个锁时间怎么理解

`lockAtMostFor` 是异常情况下的锁有效期上限，用于避免实例崩溃后锁一直占用。它不是方法执行超时，不会在时间到达时终止 Java 方法。

如果任务运行超过这个时长，锁可能已经失效，而原任务还在工作；后续触发可能获得锁并形成并发。因此需要根据最坏执行耗时留足余量，而不是随意填一个较短时间。

`lockAtLeastFor` 是最小持锁时长。即使任务很快完成，锁也至少保留这么久，帮助处理实例触发时间有偏差、任务执行过快等情况。

它并不保证“一天只执行一次”：超过最小持锁时间后，另一次触发仍可能执行。最终还需要业务状态和幂等约束。

项目的方法级配置是最大 5 分钟、最小 4 秒，会覆盖启动类的默认最大锁时间。调度规则、实例时间偏差和耗时需要一起评估。

## 五、数据库时间与实例时间

项目中 `.usingDbTime()` 被注释，不能在文档中写成已经启用了数据库时间。

对于支持的数据库，可以评估启用数据库时间来减少应用实例之间的时钟差异；具体支持情况和配置方法以项目依赖版本及官方文档为准。无论采用哪种方式，都要检查时间同步。

## 六、锁不能代替幂等

项目还会检查记录的发送标记，在发送成功后更新状态。这里仍存在外部副作用与数据库状态之间的间隙：

```text
短信平台已受理
→ Java 进程退出 / 数据库更新失败
→ 下次任务看到的状态仍然是未发送
→ 可能重复发送
```

给方法加 `@Transactional`，不能把短信平台的外部 HTTP 操作一起回滚。

可选改进包括独立发送记录、业务唯一键、原子认领状态、供应商支持的幂等请求号，以及超时后的结果对账。要先确认供应商能力，不能默认它支持安全重试。

## 七、事务和循环中的异常

项目任务外层带有 `@Transactional`，循环内又会捕获单条处理异常并记录日志。

这里不能简单认定“任何一条失败都会整体回滚”：异常是否传播、事务是否已经被标记回滚、调用经过哪些代理，都会影响结果。外部短信也不会随数据库回滚撤销。

如果任务数据量较大，可以评估分批扫描和单条/小批次事务，避免把数据库事务覆盖到长时间外部请求。事务拆分是改进方向，不是当前已经实现的行为。

项目还为后台任务设置租户上下文，并在需要时通过 `finally` 清理。这提醒我，线程池线程可能被复用，后台任务不能假设一定有 HTTP 请求携带的用户和租户信息。

## 八、如何做验证

1. 使用共享测试数据库，启动两个不同端口的实例。
2. 把 cron 暂时缩短，并用模拟短信服务记录调用次数。
3. 记录实例标识、执行批次、开始和结束时间，确认同一有效锁期间只有一个执行。
4. 模拟任务中途退出，观察锁到期后的恢复行为。
5. 故意让任务超过最大锁时长，观察后续触发是否可能并发。
6. 模拟短信成功但状态更新失败，验证业务防重策略。

实验应使用独立环境，不能在正式任务运行时随意删除锁记录或调整系统时间。

定时任务可靠性至少包含三层：调度负责何时触发，分布式锁减少同时执行，幂等与补偿处理重复和失败。理解这三层职责，比只记住两个注解更有用。
