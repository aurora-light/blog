短信发送通常有费用。如果接口允许用户连续点击、脚本反复调用，就可能产生大量无效短信。前端按钮倒计时只能改善交互，真正的频率限制必须在服务端执行。

这篇笔记来自一个 Java 后端项目中的 `AppVerificationCodeServiceImpl`。为了方便理解，下面使用通用键名和精简代码；示例不包含真实短信调用，也不代表已经做过生产压测。

## 一、为什么使用 Redis

如果只把计数放在 Java 的 Map 中，服务重启后数据就会丢失；多个服务实例也各有一份计数，无法共享额度。

Redis 可以让多个实例访问同一份状态，并通过 TTL 让状态自动失效。这里保存的是冷却标记和请求计数，不是短信验证码本身。

## 二、先区分两类限制

| 规则 | 要解决的问题 | 项目中的默认回退值 |
| --- | --- | --- |
| 手机号冷却 | 一个号码连续点击发送 | 60 秒 |
| 手机号窗口计数 | 一个号码短时间累计过多请求 | 300 秒最多 5 次 |
| IP 冷却 | 同一来源快速切换号码 | 5 秒 |
| IP 窗口计数 | 同一来源累计调用过多 | 300 秒最多 30 次 |

这些是代码在配置值不适用时采用的回退值，实际部署规则还要看配置和风控开关。拿不到 IP 时，代码会跳过 IP 维度，但继续执行手机号限制。

## 三、用带过期时间的 SET NX 实现冷却

精简后的 Spring Data Redis 示例：

```java
public void checkCooldown(StringRedisTemplate redis, String key) {
    Boolean acquired = redis.opsForValue()
            .setIfAbsent(key, "1", 60, TimeUnit.SECONDS);

    if (!Boolean.TRUE.equals(acquired)) {
        throw new IllegalStateException("发送过于频繁，请稍后再试");
    }
}
```

其中 `StringRedisTemplate` 来自 Spring Data Redis，`TimeUnit` 来自 `java.util.concurrent`。`setIfAbsent` 表示键不存在时才写入，同时指定有效期。

在支持该调用的客户端和 Redis 环境中，这对应一条带 NX 和过期参数的 SET，而不是先查询、再写入、最后设置 TTL。并发请求竞争同一个键时，只有成功创建标记的请求通过。

键的逻辑结构可以是：

```text
sms:cooldown:phone:手机号标识
sms:cooldown:ip:来源标识
```

标识要包含必要的环境、租户或业务范围，避免不同场景错误共享额度。日志应脱敏；如果不希望键中出现明文手机号，可以使用服务端 HMAC 等方式生成稳定标识。

## 四、窗口计数怎么实现

项目使用的核心思路是第一次计数时设置 TTL：

```java
Long count = redis.opsForValue().increment(key);
if (Long.valueOf(1L).equals(count)) {
    redis.expire(key, 300, TimeUnit.SECONDS);
}
if (count == null || count > 5) {
    throw new IllegalStateException("短时间内发送次数过多");
}
```

这是“从首次计数开始的固定有效期窗口”。窗口内后续请求不会刷新 TTL，超过额度的请求仍可能继续增加计数。它不是精确的滑动窗口。

为什么不在每次调用后刷新 TTL？因为持续请求会一直延长窗口，规则就变成了另一种行为。

## 五、现有实现有哪些边界

上面的 `INCR` 和 `EXPIRE` 是两个独立操作。虽然单次递增是原子的，但两步之间如果进程中断，计数键可能没有过期时间。

一个可选改进是把它们合成 Lua 脚本：

```lua
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], tonumber(ARGV[1]))
end
return count
```

脚本减少了两条命令之间被打断的窗口，但不自动修复历史上已经没有 TTL 的键，也不等于发生错误时自动回滚。生产使用前仍要验证参数、序列化及异常策略。Redis 对脚本的执行保证可参考[官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)。

另一个边界是四项规则按顺序执行。如果手机号冷却已经写入，后面的 IP 规则失败，之前的标记不会自动撤销。因此，当前额度统计的是走到相应检查位置的尝试，不是最终成功送达的短信数。

## 六、把检查放在什么位置

推荐的逻辑顺序是：

```text
校验请求参数
→ 检查风控开关
→ 可选的一次性令牌校验
→ 手机号和 IP 频率检查
→ 调用短信供应商
→ 记录发送结果
```

项目在令牌检查后再执行频率限制，这意味着后续限流或短信失败时，令牌可能已经消费。这是需要理解的行为，不能把令牌“只能用一次”误解为“保证发送成功”。

客户端 IP 只能基于可信网关的转发规则提取，不能无条件相信用户提交的请求头。公司出口、家庭网络也可能共享 IP，所以 IP 限额要结合手机号维度使用。

Redis 不可用时是放行还是拒绝，需要显式约定。短信有成本，不能直接照搬普通页面接口的故障放行策略。

## 七、怎样验证

使用隔离测试 Redis，并把短信供应商替换成假的实现，避免测试产生费用：

1. 同一号码连续调用，第二次应在冷却期内被拦截。
2. 用不同测试键单独验证窗口计数，确认第 6 次触发限制。
3. 检查计数键 TTL，确认后续请求没有一直延长有效期。
4. 并发竞争同一个冷却键，验证只有一个成功。
5. 测试 IP 缺失、Redis 超时、供应商失败时的实际行为。

如果通过完整业务链路测试窗口，需要等待冷却或在测试配置中缩短间隔，否则可能一直停在冷却检查，根本没有覆盖到窗口逻辑。

学习这部分代码后，我更愿意把限流理解为一组业务规则：限制谁、持续多久、统计尝试还是成功，以及系统出错时怎样处理。Redis 命令只是实现这些规则的工具。
