在短信验证码接口中，我看到一段很短的 Lua 脚本：读取 Redis 中的令牌，检查绑定的手机号，匹配后删除。

为什么不直接用 Java 先 GET，再 DEL？要理解它，需要先区分“单条命令安全”和“一组操作不可分割”。

本文基于项目中的短信请求令牌流程，示例使用通用命名。本文讨论的是发送短信前的请求凭证，不是登录会话 token，也不是用户收到的短信验证码。

## 一、令牌在流程中做什么

```text
客户端申请请求凭证
→ 服务端生成随机令牌
→ Redis 保存令牌与手机号的绑定，并设置 TTL
→ 返回令牌、时间戳与签名
→ 客户端携带凭证请求发送短信
→ 服务端校验并消费令牌
```

项目使用安全随机数生成令牌，并采用 HMAC-SHA256 对手机号、验证码类型、令牌和时间戳组成的固定格式内容签名。密钥只保留在服务端。

各部分职责不同：

| 内容 | 职责 |
| --- | --- |
| 随机令牌 | 提供难以猜测的请求标识 |
| Redis TTL | 限制令牌在服务端的存活时间 |
| 时间戳检查 | 限制凭证的时间范围 |
| HMAC 签名 | 检测被绑定字段是否遭到修改 |
| 原子消费 | 防止同一令牌被重复使用 |

签名不是加密，不会隐藏手机号；如果合法凭证被窃取，也不能仅靠签名阻止它被使用。传输仍需要 HTTPS。

## 二、先 GET 再 DEL 为什么不够

看似合理的代码：

```java
String owner = redis.opsForValue().get(tokenKey);
if (phone.equals(owner)) {
    redis.delete(tokenKey);
    sendSms();
}
```

两个请求可能这样交错执行：

```text
请求 A：GET，读到手机号
请求 B：GET，也读到手机号
请求 A：校验通过，DEL
请求 B：校验通过，DEL
请求 A、B：都继续发送短信
```

示例没有判断删除结果，所以两个请求都能通过。即使修改为检查 DEL 返回值，仍然需要仔细处理“读取值”和“删除键”之间的条件关系；把比较与删除放在一起更直接。

在一个 Java 进程内使用 `synchronized` 也不能协调另一个服务实例，检查必须在共享状态所在的位置完成。

## 三、用 Lua 原子地比较并删除

项目的脚本可以整理为：

```lua
local tokenValue = redis.call('GET', KEYS[1])
if not tokenValue then
    return 0
end
if tokenValue == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return -1
```

这里 `KEYS[1]` 是令牌的 Redis 键，`ARGV[1]` 是本次请求的手机号。

返回值约定如下：

- `1`：匹配并成功删除，可以继续。
- `0`：令牌不存在，可能已过期或已消费。
- `-1`：令牌存在，但绑定的手机号不匹配。

不要在脚本之外先删除再比较，否则错误手机号也能消耗别人的凭证。

Redis 保证脚本执行期间不会被其他客户端命令穿插，因此并发请求只有一个能完成匹配删除。但脚本应当短小，不能执行长循环；原子执行也不意味着脚本错误会撤销之前的写入。[Redis Lua 官方说明](https://redis.io/docs/latest/develop/programmability/eval-intro/)

## 四、Java 如何调用

以下为使用 `StringRedisTemplate` 的精简片段，需要 Spring Data Redis 依赖，运行时需要可连接的测试 Redis：

```java
String lua = "local v = redis.call('GET', KEYS[1]); "
        + "if not v then return 0; end; "
        + "if v == ARGV[1] then return redis.call('DEL', KEYS[1]); end; "
        + "return -1;";

RedisScript<Long> script = RedisScript.of(lua, Long.class);
Long result = redis.execute(
        script,
        Collections.singletonList(tokenKey),
        phone
);

if (!Long.valueOf(1L).equals(result)) {
    throw new IllegalStateException("请求凭证无效或已使用");
}
```

这里使用 `Long` 接收结果，不能通过引用相等判断包装类型的数值。键和值的序列化方式也必须一致，否则 Redis 保存的值与脚本参数可能不是同一串字节。

脚本访问的键通过 `KEYS` 传入；不要在 Lua 中随意拼接其他未声明的键。多键脚本还需要考虑 Redis Cluster 的 hash slot 约束，本例只有一个键。

## 五、消费前还需要什么检查

项目在执行 Lua 前先校验：

1. 凭证字段是否齐全。
2. 时间戳格式和时间范围是否合法。
3. 根据相同字段和格式重新计算签名。
4. 使用 `MessageDigest.isEqual` 比较签名字节。
5. 最后原子消费 Redis 令牌。

签名字段的顺序、编码、空值规则必须固定。如果生成和校验使用不同格式，同一份合法数据也会验证失败。

令牌申请接口本身也需要防刷；否则攻击者仍可以不断申请合法令牌。一次性凭证需要与手机号/IP 限流共同工作。

## 六、一次性不等于业务只成功一次

项目会先消费令牌，再检查发送频率并调用短信服务。因此，后续流程失败时，客户端不能继续复用旧令牌，需要重新申请。

这带来一个明确取舍：同一凭证最多放行一次后续尝试，但不能保证这次尝试一定发送成功，也不保证外部系统绝不会重复处理。

如果业务要求重试返回同一个结果，应另外设计幂等请求号、处理状态与结果查询。防重放令牌和业务幂等不是同一个概念。

## 七、测试清单

| 场景 | 预期 |
| --- | --- |
| 正确手机号首次消费 | 返回 1，键被删除 |
| 相同凭证第二次消费 | 返回 0 |
| 错误手机号消费 | 返回 -1，原键保留 |
| 令牌过期 | 返回 0 |
| 多个线程竞争一个令牌 | 只有一个返回 1 |
| 修改手机号或时间戳 | 在签名校验阶段被拒绝 |
| 消费后短信服务失败 | 旧令牌不能再次使用 |

测试使用独立键前缀和模拟短信服务，结束后只清理测试数据。不要把签名密钥、完整令牌和明文手机号输出到日志。

这段脚本让我理解了一个常见并发原则：如果业务要求“满足条件才修改”，就应考虑如何把条件检查和状态修改放进同一个原子操作。
