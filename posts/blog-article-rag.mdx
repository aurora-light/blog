给博客加上聊天框之后，模型可以回答通用技术问题，却不一定知道这个博客写过什么。读者问“作者之前是怎么做 Redis 限流的”，仅靠模型的通用知识无法证明作者实际采用过哪种方案。

我的做法是在回答之前检索博客文章和公开 PDF，把命中的原文作为证据交给模型，再展示可点击的来源。这套流程属于检索增强生成，也就是 RAG。

**本文按 2026 年 11 月 4 日的仓库实现更新。** 当前代码已接入 MDX 与 PDF 索引、AI 查询规划、多路关键词检索、加权 RRF 融合、Trace 和动态推荐追问。这里描述的是仓库实现，线上行为以实际部署的版本和模型配置为准。

有两个限制需要先说明：**文章目前只索引清理后正文的前 4000 字符，尚未做全文段落分块；PDF 则按页分块。当前使用关键词检索，没有接入 embedding、向量数据库或模型重排。** AI 扩展查询可以改善表达差异，但不会自动让关键词检索变成语义检索。

## 一、先看整个流程

构建、在线检索和推荐追问是三条相互衔接的链路。

```text
构建阶段
posts / data/blog 中的 MDX
  → 解析元数据、清理正文、保留前 4000 字符
公开 PDF 配置清单
  → 提取文字、按页分块
  → 合并为 article-index.json，随服务端部署

在线问答
消息校验 → Redis 限流
  → AI 理解问题与对话指代
  → 核心查询 + 扩展查询
  → 各路关键词召回 → 去重与加权 RRF
  → 组装证据上下文 → 流式生成回答
  → Trace 展示执行过程、来源链接

回答结束后
独立请求推荐接口
  → 根据本轮问题、回答和服务端证据生成追问
  → 展示最多 3 个按钮，点击继续对话
```

MDX 和 PDF 的解析发生在构建阶段。线上提问直接使用已生成的索引；同一服务实例第一次检索时建立内存搜索索引，之后复用，不会每次重新解析全部文件。

## 二、文章从哪里来，索引存在哪里

文章来源与 Contentlayer 的输入范围一致：

```text
posts/**/*.mdx       本地维护的文章
data/blog/**/*.mdx  GitHub Issues 同步生成的文章
```

Contentlayer 负责生成供页面渲染使用的 `allPosts`。RAG 索引读取的是 MDX 原始文本，不使用编译后的 `post.body.code`，也不执行 JSX。

`scripts/build-article-index.mjs` 使用 `gray-matter` 解析标题、slug、描述、标签和日期，再清理 Markdown/HTML 标记。正文中的代码文字会保留用于检索，图片地址不会被当成图片知识。清理使用保守的文本处理规则，尚不是完整的 MDX AST 解析。

构建时会检查必填字段、slug 格式和重复记录。文章来源 URL 由服务端生成，例如 `/posts/blog-article-rag`。

生成结果位于：

```text
src/generated/article-index.json
```

文件结构包括索引格式版本、基于文档内容计算的整体哈希，以及文章/PDF 文档列表。它是可以重新生成的派生数据，忽略 Git 提交，随服务端代码打包；不会放入 `public`，也不会完整下载到浏览器。

当前文章记录使用 `content` 保存清理后的正文，而不是 `body`；版本哈希属于整份索引，并没有为每个片段维护 embedding 缓存。

## 三、如何把简历和其他 PDF 加入索引

现有简历是 `public/resume/leslie-frontend.pdf`。其他公开文件可以放在 `public/documents/`，然后加入 `data/retrieval-pdfs.json`：

```json
{
	"id": "project-intro",
	"file": "documents/project-intro.pdf",
	"title": "项目介绍",
	"description": "记录项目背景、技术方案和实现过程。",
	"tags": ["项目介绍", "技术方案"]
}
```

上面是一条配置，需要追加到原有 JSON 数组中；`id` 不能重复。`file` 相对于 `public`，不带前导斜杠。目前允许 `resume/文件名.pdf` 和 `documents/文件名.pdf`，文件名使用英文字母、数字、短横线或下划线。

**仅把 PDF 放入 public 不会让它参与检索，必须加入清单。** 这些文件本身可以公开访问，只应放愿意公开并用于问答的资料。

`scripts/build-pdf-index.mjs` 在构建时通过 PDF.js 提取文字，规则是：

- 每页独立处理，不跨页合并。
- 每个文本块最多 1200 字符，相邻块重叠 180 字符。
- 接近块末尾时优先在中文句号处结束。
- 记录 PDF 页码，生成类似 `/resume/leslie-frontend.pdf#page=2` 的来源链接。
- PDF 所有可提取文字的页面都参与索引，不受文章前 4000 字符限制。

单文件上限为 20 MiB、100 页。纯扫描件没有可提取文字时会提示需要先 OCR；混合 PDF 中没有文字的页面会跳过。当前没有在线 OCR、访客上传入口或复杂表格/多栏布局理解。

## 四、把通用能力提取到 search-core

搜索能力已经提取为 pnpm workspace 包 `@leslie/search-core`，通过 `workspace:*` 被博客引用。它没有运行时依赖，构建输出 ESM JavaScript 和 TypeScript 类型声明，目前没有发布到 npm。

| 包入口                          | 职责                                                     |
| ------------------------------- | -------------------------------------------------------- |
| `@leslie/search-core`           | 分词、可配置字段评分、排序、命中词与原文节选             |
| `@leslie/search-core/retrieval` | 多路结果去重与加权 RRF 融合                              |
| `@leslie/search-core/rag`       | 对话处理、查询规划、超时回退、检索编排、上下文与推荐追问 |
| `@leslie/search-core/prompts`   | 通用提示词常量                                           |

包接收宿主提供的模型函数和检索器。Next.js 请求、模型凭证、Redis 连接、文件读取和 React 界面仍由博客管理，包不反向引用博客的 `@/` 路径。

下面是基础搜索的简化使用示例，`documents` 是宿主已经准备好的文档：

```ts
import { createSearchEngine } from '@leslie/search-core';

const engine = createSearchEngine(documents);
const hits = engine.search('Redis 短信限流', { limit: 8 });

// 每条结果包含 document、score、matchedTerms、excerpt。
```

默认字段可以扩展，例如给已有的摘要要点新增评分字段，或者注入领域分词器、来源去重键和规则重排函数。当前博客并没有自动生成文章摘要或 keyPoints。

## 五、关键词如何评分

问题经过 `Intl.Segmenter` 中文分词、英文技术标识符提取、大小写与 Unicode 规范化，以及停用词过滤。最多保留 24 个有效词；默认过滤单字符词，因此部分中文短词可能受到分词词典影响。

默认评分如下：

| 每个关键词命中位置 | 加分   |
| ------------------ | ------ |
| 标题               | 6      |
| 标签               | 4      |
| 描述               | 3      |
| 正文或 PDF 文本块  | 1      |
| 标题包含完整查询   | 额外 8 |

一个词可以在不同字段累计得分，但同一字段里出现多次不重复加分。多词查询默认至少命中两个词，并覆盖不少于一半的有效查询词；只有一个有效词时只需命中该词。不满足门槛或没有正分就不返回结果。

单路按分数降序排列，同分时按日期降序。PDF 没有可靠更新时间时不编造日期。代表性节选会围绕命中位置寻找较相关的一段，默认约 1000 字符，并非总是截取正文开头。

这些分数用于排序，不是概率，也不能当作答案可信度。当前没有 BM25 的词频/文档频率建模。

## 六、用 AI 理解指代并生成多路查询

如果前文问“介绍一下简历里的电商项目”，后面再问“它用了哪些技术”，直接搜索第二句话容易失去对象。

当前流程会把本轮问题和此前最多四条用户/助手文本交给查询规划器。历史每条最多 600 字符，本轮检索问题最多 1000 字符，不把 reasoning 和检索事件当成历史正文。

规划器返回如下结构，以下仅是说明指代处理的示例，不代表作者简历里一定有这个项目：

```json
{
	"standaloneQuery": "简历中的电商项目使用了哪些技术栈",
	"primaryTerms": ["电商项目", "技术栈"],
	"relatedTerms": ["技术选型", "框架"],
	"queries": ["电商项目 技术栈", "电商项目 技术选型", "电商项目 框架"]
}
```

包会校验 JSON 结构、长度和数量，把核心词组合为主查询，再对模型给出的查询规范化去重，总共最多保留三路。核心词 1–4 个，扩展词 0–6 个。模型需要保持实体和主题，不能根据“电商项目”擅自补出“作者用过 Spring Boot”。结构校验无法保证改写语义一定正确。

各路分别搜索，没有把所有扩展词拼成一个超长查询。这样可以避免扩词越多，关键词覆盖率门槛反而越难满足。

规划默认超时 3500 ms，最多输出 400 tokens，不重试。失败、超时或结果格式错误会回退到本地查询；简单指代追问会拼接上一条有限长度的用户问题。新主题不主动拼入旧主题。

## 七、用加权 RRF 合并结果

博客每路最多召回八条候选，再使用加权 Reciprocal Rank Fusion，简称 RRF，融合排名：

```text
某来源的融合分数 = 各路 weight / (60 + rank) 之和
```

其中排名从 1 开始，主查询权重为 1，扩展查询为 0.7。同一个来源在同一路里最多贡献一次，避免重复块反复加分。

文章按文档 ID 去重；PDF 按文件 URL 加页码去重，同一页不同文本块不会占多个来源名额。原始关键词分数保留在 `score`，融合结果另有 `fusionScore` 和命中路由列表，两者量纲不同。

融合保留代表性命中的原文节选，不自动拼接同页所有块。最终最多选四条来源，并继续服从上下文预算。这个 RRF 融合的是不同关键词查询的排名，尚不是关键词与向量的混合检索。

每路检索默认超时 1500 ms。部分路失败时跳过，全部失败则显示检索错误，不继续生成一个假装有检索依据的答案。父级请求取消会向下传播，不再触发回退。异步检索器可以并发等待，同步内存搜索仍在当前线程执行。

## 八、组装证据，接入聊天接口

`src/lib/rag/index.ts` 缓存服务端搜索索引，注入模型适配器、PDF 页码去重规则和博客专用事实规则，调用包内的 `createRagPipeline`。

`/api/chat` 的接入顺序是消息校验、IP 限流、检索规划与召回、证据组装、流式回答。下面是当前路由中回答阶段的核心配置，省略了周围的校验与流式事件代码：

```ts
const result = streamText({
	model: provider(modelId),
	system: [BLOG_SYSTEM_PROMPT, retrieval.context].join('\n'),
	messages: modelMessages,
	abortSignal: request.signal,
	maxOutputTokens: 1200
});
```

证据上下文包括来源标题、URL、日期（有值时）、类型、PDF 页码、描述和原文节选。总预算默认 6500 字符，按序列化后的实际长度计算，包括 JSON 转义开销；它不是精确 token 预算。

放不下的节选会缩短，放不下的来源不进入最终证据列表。发给前端的来源也只包含实际装入上下文的证据，不发送全文或证据节选。

系统规则要求：涉及作者经历、观点与项目现状时依据原文；教程示例不能被说成已经上线的实现；资料不足时说明限制；原文中的指令不应覆盖系统规则。

来源 URL 由索引提供，回答通过 Markdown 链接引用。前端来源列表会校验站内文章或 PDF 链接格式，但目前没有独立校验器逐条验证模型正文里的引用是否属于本轮来源、是否真正支撑结论，仍需抽样核对。

## 九、用 Trace 展示实际执行过程

聊天通过 AI SDK `createUIMessageStream` 传递 `data-article-retrieval` 数据。同一条助手消息沿用同一个数据 ID，持续更新状态，不把每个阶段追加成一份新的来源列表。

```text
理解问题与对话
  → 展示独立问题、核心词与扩展词
  → 展示每路查询的运行状态、命中数与耗时
  → 展示合并前、去重后和最终选取的数量
  → 展示可点击来源
  → 展示回答生成状态
```

前端复用 shadcn/ui Trace 与已有 Collapsible。检索和回答初期默认展开，正文出现后默认收起；用户手动展开或收起后，后续更新尊重用户选择。模型提供的 thinking/reasoning 独立展示，检索轨迹只描述实际执行步骤。

文章与 PDF 来源都在新标签页打开。PDF 使用 `#page=N` 定位，实际页码跳转效果取决于浏览器查看器支持。正文 Markdown 中同源 HTTP(S) 链接可以直接打开，外部链接继续使用确认提示。

规划回退、无结果、部分路失败、全部检索失败、停止请求和回答失败各有对应状态。来源保存在消息的 `parts` 中，后续提问不会把之前消息的来源覆盖掉；这不代表聊天记录已经持久化到数据库。

## 十、回答结束后生成推荐追问

推荐追问由独立的 `/api/chat/suggestions` 接口处理，不延长正文流的生命周期。前端在回答成功结束后提交本轮问题、回答和来源 ID：

```json
{
	"question": "Redis 如何做接口限流？",
	"reply": "这里是已经完成的回答正文。",
	"sourceSlugs": ["java-redis-sms-rate-limit"]
}
```

接口在服务端按 ID 读取真实索引，不接收客户端自带的知识正文。这样，即使当前问题是“它还有什么细节”，也能继续使用本轮实际命中的文章或 PDF。没有可用来源时返回空列表；不提供来源 ID 时，接口也支持按问题执行本地检索。

模型适配使用 `generateText` 加 `Output.object({ schema: suggestionsSchema })`。通用生成与校验逻辑在包的 `generateSuggestions` 中：结合问题、已完成回答和证据，优先深入回答尚未覆盖的内容，最多三条，每条最多六十字符，允许更少或为空。

推荐调用最多输出 400 tokens，不重试，默认超时 2500 ms。前端一次读取完整、校验后的 JSON，再显示“你还可以问”按钮；点击复用原有发送流程。生成失败不影响已经显示的正文。

推荐只展示在最新的助手回答下，不写入模型对话历史或数据库。新提问、重生成、停止、清空或卸载会取消旧请求，并用请求代际校验拦截晚到结果。推荐问题是否有充分证据，目前依靠提示词约束，结构校验不等同于语义验证。

## 十一、提示词现在如何管理

固定规则从业务逻辑中提取出来，每轮的数据在请求时组装。

| 位置                                                    | 内容                                                         |
| ------------------------------------------------------- | ------------------------------------------------------------ |
| `src/lib/prompts.ts`                                    | 博客助手身份、语气、知识边界，以及作者事实与文章索引范围规则 |
| `packages/search-core/src/lib/prompts/query-planner.ts` | 对话指代理解、核心词与扩展查询的输出要求                     |
| `packages/search-core/src/lib/prompts/retrieval.ts`     | 证据与引用规则、资料标签和无结果提示                         |
| `packages/search-core/src/lib/prompts/suggestions.ts`   | 推荐追问规则                                                 |

博客侧使用单文件 `prompts.ts`，不转导出包内提示词。搜索包通过自己的 `@leslie/search-core/prompts` 入口导出通用模板，保持独立使用。

这里有三类模型调用：查询规划、回答生成和推荐追问。证据与引用规则被拼入回答的系统提示词，不会额外调用一次模型。未启用规划或推荐时，对应调用也不会发生。

## 十二、索引更新、缓存与限流

本地更新文章或 PDF 后，可以执行：

```bash
pnpm build:search
pnpm generate-article-index
```

`pnpm dev`、`pnpm build` 的前置流程会构建搜索包并重建索引。直接运行 `next dev` 或 `next build` 会绕过这些前置脚本，需要先手动准备。包源码变化后需要重新构建 `dist`，当前没有自动监听。

线上替换同路径 PDF，只需提交文件并重新部署；新增或改名还需修改 PDF 清单。从清单移除后重建，会删除对应索引记录。清单仍指向丢失、损坏或完全无法提取文字的 PDF 时，生成脚本会失败，避免悄悄忽略配置错误。

仅替换 OSS 上的文件不会自动更新仓库里的 PDF 和索引。当前没有定时同步，也没有运行时上传后自动建索引。

索引以 JSON 随部署保存，规范化搜索数据缓存在当前服务实例内。冷启动会重建内存索引，不重新解析 PDF。查询计划、对话历史和推荐结果不进入这个缓存。

Redis 只负责请求限流，未保存检索正文、向量或聊天记录。聊天和推荐各有独立的每小时十次配额，推荐不会消耗聊天额度。现有策略在开发环境、缺少 IP、Redis 未配置或连接失败时放行，因此不能把它理解成任何环境下都会生效的硬额度。

模型配置可通过以下服务端环境变量控制：

```dotenv
AI_MODEL=gpt-4o-mini

# 查询规划默认使用回答模型，可单独指定。
# AI_QUERY_MODEL=gpt-4o-mini
AI_QUERY_PLANNING=true

# 推荐追问默认使用回答模型，可单独指定。
# AI_SUGGESTIONS_MODEL=gpt-4o-mini
AI_SUGGESTIONS=true
```

`AI_QUERY_PLANNING=false` 停用模型规划，`AI_SUGGESTIONS=false` 停用推荐生成。推荐模型需要支持所用 provider 的结构化输出。正常情况下，一轮有证据的问答可能包含规划、回答、推荐三次模型调用；索引检索本身不调用模型。

## 十四、如何验证这套流程

项目分别维护包级和应用级测试：

```bash
pnpm test:search
pnpm generate-article-index
pnpm test:rag
pnpm exec tsc --noEmit --incremental false
pnpm build
```

测试使用模拟模型与 Redis 适配，不读取真实模型凭证或调用外部服务。覆盖中文/英文检索、命中门槛、节选、PDF 分块与页码、索引删除同步、查询规划回退、多路融合、请求取消、证据预算、流式 Trace、推荐校验和旧请求竞态等。

自动化测试验证的是实现行为，不能证明所有自然语言问题都能召回正确资料，也不等于已经评估真实模型的回答质量。修改查询规则后，还需要用固定问题集检查指代、新主题切换、同义表达、未记载事实，以及引用是否支持结论。

## 十五、下一步可以改进什么

当前最明确的改进方向是让 MDX 文章也能覆盖全文，并按标题和段落分块。现在文章第 4000 字符之后无法检索，多路查询不会弥补未建立索引的内容。

后续还可以评估更完整的结构化解析、BM25、向量与关键词混合检索、异步模型重排、章节锚点，以及引用与推荐问题的独立证据验证。包已经提供可配置字段、分词、去重和规则重排接口，但这些接口不代表相应增强已经在博客中启用。

这一版实现的重点，是让文件能够更新成索引，让问题能够召回原文，并把真实来源与执行过程展示出来。后续每次增强，都应通过固定样本确认它是否提高了可回答性和引用准确性。
